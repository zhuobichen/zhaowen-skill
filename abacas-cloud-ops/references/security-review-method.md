# 前端驱动的多租户 SaaS 后端安全评估方法

> 本文只记录**方法**。不含任何具体目标的漏洞结论、凭据、业务数据或源码。
> 评估对象若为他人系统，动手前先拿到书面授权，并遵守文末 §8 的边界纪律。

适用于这类形态的系统：**未混淆的 SPA 前端 + OIDC/OAuth2 登录 + 网关聚合多个后端微服务 + 多租户数据**。
典型例子是 Vue3/Vite 打包的业务平台、政务或科研类 SaaS。

核心立场一句话：**前端 bundle 能告诉你"有哪些接口"，但绝不能告诉你"谁被允许调用"**。
所有授权结论必须来自后端的运行时响应。

---

## 1. 阶段划分

| 阶段 | 输入 | 产出 | 是否需要凭据 |
|---|---|---|---|
| 一 · 静态测绘 | 生产站点 JS bundle | API 全量清单、认证机制、客户端功能开关 | 否 |
| 二 · 认证测绘 | OIDC discovery 文档 | 客户端类型、token 端点、audience 绑定 | 否 |
| 三 · 授权假设 | 阶段一结果 | 待验证的授权模型假设 | 否 |
| 四 · 运行时验证 | **低权限账号 token** | 隔离维度、越权结论、可利用性定级 | 是 |

阶段一至三是纯读操作，可以无凭据完成。**阶段四之前不要下任何授权结论。**

---

## 2. 阶段一：从 bundle 反推 API 全量清单

Vite/Vue 生产构建**通常不混淆**（无变量重命名、无控制流平坦化），压缩只影响空白，
字符串字面量、路由表、API 调用点全部保留。所以可以静态穷举。

在 bundle 目录下按服务前缀归组提取 `verb + path`：

```powershell
rg -o --no-filename '"/[a-z][a-z0-9-]{2,30}/api/[A-Za-z][A-Za-z0-9/{}_-]*"' .
```

要点：

- **按前缀分组**，一个网关服务一个前缀。分组之后你才看得出"有几个独立后端"，而这决定了横向越权要逐个服务验证，不能只测一个。
- **保留来源文件**。每条路径记录它出现在哪个 js 文件里，后续回溯参数结构时省事。
- **注意模板字符串拼出来的路径**。形如 `` `${base}/api/${kind}/${id}` `` 的写法，静态正则只能看到片段。漏掉的通常正是带 `{id}` 的单体端点——而那恰恰是 IDOR 的落点。
- 产物写成机器可读的 `api-all.json` / `paths.json`，后续阶段直接消费。

### 同时要记的"不该出现在包里"的东西

内网主机名、后端直连地址、调试开关、租户/地域开关常量。
这些是信息泄露的候选，但要**先验证可达性和鉴权**再定级——
一个返回 401 的内网地址只是信息泄露，返回 200 才是攻击面。

---

## 3. 阶段二：认证机制测绘

从 bundle 提取 OIDC 客户端配置（issuer、client_id、token endpoint、resource/audience）。
公共客户端（SPA）用 PKCE + `token_endpoint_auth_methods_supported: none`，这是**正确配置**，看到 `none` 不要报为漏洞。

必须核对的两件事：

1. **issuer 是否反射 Origin 且带 `Access-Control-Allow-Credentials: true`**。带 CORS 但不带 ACAC = 正常；两者同时有才有问题。
2. **`scope` 是否为空**。见 §5，这是后端能不能做粗粒度授权的前提。

---

## 4. 阶段三：客户端授权代码的静态审计

对 SPA 来说，最典型的误判是"前端没做权限控制 = 越权漏洞"。**不是**。
前端路由守卫、菜单过滤、按钮显隐几乎从来不是安全边界，只是 UX。

静态审计要找的是**证据**，不是风险：

- 角色信息解析进状态库之后，**是否还有任何引用**？一个实用判据：`roleNames` / `roles` 在整个构建产物里只出现一次（解析处），说明它从未参与任何决策。
- 按钮级权限（`canEdit` / `canDelete` / `canExport`）的**数据来源**。如果来自服务端下发的标志位，那它是服务端授权的 UI 呈现，不是客户端授权。
- 客户端功能开关（feature flag）**是否随请求上行**。只存在于本地状态、从不进请求体或 query 的开关，是纯客户端开关——它只决定调哪个后端能力，**真正的权限边界在后端那个能力上**。

这一阶段的正确产出是**一组待验证假设**，写成"后端是否按 X 校验"，而不是"存在越权"。

## 5. 阶段四：运行时验证（关键技法集）

前置：拿到**低权限账号**的 token。管理员 token 测不出越权——服务端对管理员本来就全放行。
能用 refresh_token 就别要密码。

### 5.1 JWT 载荷本地解码（不发任何请求）

base64url 解第二段，**注意补 padding**（PowerShell）：

```powershell
$p = ($t -split '\.')[1].Replace('-','+').Replace('_','/')
switch ($p.Length % 4) { 2 {$p+='=='} 3 {$p+='='} }
[Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($p)) | ConvertFrom-Json
```

逐条读这几个字段：

| 字段 | 读出什么 |
|---|---|
| `roles` | 权限粒度。若只有 `["user"]`，测试账号合格 |
| `scope` | **为空字符串 = 网关没有粗粒度授权可依据**，只剩身份 |
| `sub` | 不透明标识（常见形态：非 UUID、非邮箱），后续比对的基准 |
| `aud` | token 被限定到哪个资源服务。跨服务复用是否被拒，是独立检查项 |
| `exp - iat` | token 生命周期 |

**`scope` 为空 + `sub` 不透明**，直接推出一个结论：隔离只能发生在"用户"层，不可能发生在"租户/组织"层——因为 token 里没有可依据的租户信息。
这句话往往是整份报告里最有价值的一句，但还需要 §5.2 验证库里确实也没有。

### 5.2 归属分布统计 —— 判定是否按用户隔离

拉一次集合端点，**落盘**（不要打进对话），然后统计归属字段：

```powershell
rg -o --no-filename '"(createdBy|ownerId|updatedBy)":"[^"]*"' data.json | Group-Object
rg -o --no-filename '"(tenant|tenantId|orgId|provinceCode|cityCode|organization)":' data.json | Group-Object
```

判读：

- 归属字段全部 == token 的 `sub` → **按用户隔离成立**，客户端无授权的发现要降级。
- 出现别的 `sub` → 水平越权成立，直接 High。
- 租户类字段**零命中** → 确认隔离维度就是"用户"，据此向甲方确认业务模型。

### 5.3 404 还是 403 —— 存在性预言机

挑**明确不属于本账号**的 id 单次探测：

- `403 Forbidden` → **存在性预言机成立**：能区分"存在但无权限"和"不存在"。
- `404 Not Found` 且响应体只回 `... was not found` → 姿态正确，不泄露存在性。

残余不确定性要说清：单账号**无法区分"被过滤"和"已删除"**。要收口必须第二账号。
不要用"没测出来"当"没问题"，也不要用"可能有问题"当结论——写进报告的应是"未证明，且因缺第二账号无法排除"。

### 5.4 TTFB —— 区分服务端开销与带宽开销

整改方案完全取决于成本发生在哪侧：

```powershell
curl.exe -sS --max-time 15 -o NUL `
  -w "TTFB=%{time_starttransfer}s  已收=%{size_download}B`n" `
  -H "Authorization: Bearer $t" "<集合端点>"
```

用 `--max-time` 掐断，拿首字节时间：

| TTFB | 含义 | 整改方向 |
|---|---|---|
| ≈ 0 | 流式输出，边查边发 | 服务端 CPU/DB 成本跑不掉，**加缓存或 CDN 救不了** |
| ≈ 总耗时 | 阻塞式构建完才发 | 单次内存峰值，可能撑爆 worker 池 |

`%{size_download}` 配合 `--compressed` 才能拿到线上真实传输量。
**注意：压缩只影响传输，不影响服务端构建成本**，两件事要分开说。

### 5.5 集合端点 vs 单体端点 —— 载荷对比

同一 token、同一资源，只把集合换成单体：

| 请求 | 压缩后体积 |
|---|---|
| `GET /api/<Resource>`（N 条） | ? |
| `GET /api/<Resource>/<自己的一条 id>` | ? |

若单体是几 KB 而集合是几百 MB，**这直接证明集合端点内嵌的大字段不是列表渲染所必需的**。这是两条结论的同一个证据：

1. 可用性：集合端点无分页 → 单请求即产生大量 CPU/内存/出口，且可并发触发。
2. 数据最小化：全量下发超出必要范围的业务参数（常含人口、经济、地理等敏感参数）。

整改优先级应该排在最高——**一次字段投影改造同时解决两个问题**。

### 5.6 落盘文件被截断时的 id 区间分析

大响应一定会超时截断。这时"我没拿到的 id"有两种可能：**不属于我**，或者**被截断了**。

不区分就下"越权未成立"的结论是错的。判据：

```powershell
$ids = @(rg -o --no-filename '"id":\d+' data.json |
         ForEach-Object { [int]($_ -replace '\D','') })
($ids | Sort-Object) -join ',' -eq ($ids -join ',')   # 是否单调
```

**序列单调（升序或降序）时，截断只影响一端**，另一端是完整覆盖的，完整区内缺失的 id 才能作为越权探测目标。

序列非单调 → 文件中部就有洞，缺失 id 的归属无法判定，需要重新完整拉取。

### 5.7 CORS 检查

逐个 Origin 值试：`https://evil.example.com`、以及 **`Origin: null`**（sandbox iframe、`data:`、`file://` 都会发出 `null`，很多检查漏掉这个）。

反射任意 Origin 本身不是漏洞，成色取决于认证方式：

- **Bearer header 认证** → 直接跨源窃取凭据不成立（浏览器不会自动带 header）。
- **Cookie 认证** → 立即是完整账号接管。
- 中间态（`null` + ACAC）→ 沙箱 iframe 可读已认证响应，属于真实风险，且**一旦将来引入 cookie 认证就自动升级**——报告里要写明这个演进路径。

### 5.8 Cookie 与安全响应头

```powershell
curl.exe -sS -D - -o NUL "<任一静态资源>"
```

不带 cookie 请求，看服务端是否**主动下发**会话 cookie。判读要点：

- 一个纯缓存/会话亲和 cookie 挂 `Max-Age=86400` 且全域，**该做的是去掉它，不是补标志位**。
- `HttpOnly` 挡住 JS 读取（有效），但**挡不住**明文 HTTP 外发——缺 `Secure` 仍然泄漏。
- 缺 `SameSite` 时，结论要写清"依赖浏览器默认 Lax 兜底"，而不是"已设置"。
- HSTS 同指令重复下发属畸形头。

## 6. 子域与兄弟应用

主站的 CORS/响应头正确，**不代表兄弟子域一致**。逐个子域独立检查：是否公网可达、CORS 是否反射任意 Origin、安全响应头基线是否与主站一致。

三者不一致本身就是一条发现——说明没有统一的安全基线，修复要落到配置管理而不是单个站点。

另外查一下**本地代理/桥接进程**（Electron 客户端、桌面助手类）：

- 绑 `127.0.0.0/8` 还是 `0.0.0.0`（后者局域网可达）
- CORS 中间件是否 `allow_origins=["*"]`
- 哪些端点需要会话头，哪些不需要——不需要的那些就是跨源可打的
- 远程命令是否正确引用参数（`"$1"` 而非裸 `$1`）

这条链的杀伤力通常不在单个端点，而在**跨源可达 + 无需认证 + 能读到内网信息**的组合。

## 7. 报告纪律

1. **区分"已证明"与"未证明"**。写"未证明，且因缺条件无法排除"，不要写"不存在问题"。
2. **给证据也给残余不确定性**。每个结论标注是实测还是静态推断。
3. **降级要写降级依据**。降级本身是可辩护的专业判断，不是软化。
4. **待甲方确认的业务问题单列**。授权模型（按人 vs 按单位）、注册门槛、WAF 有无，这些不是漏洞，是决定定级的前提，混进结论会让整份报告失去可信度。
5. **可利用性前提要显式标注**。"若前置 WAF 则可利用性下降"这类前提必须写进定级段落。

## 8. 边界纪律（最重要的一节）

技术可行 ≠ 应当实施。以下几条是硬线：

| 动作 | 边界 |
|---|---|
| 未认证 GET / 静态审计 | 可做 |
| 自有低权账号的单次授权探测 | 可做 |
| **别人的账号 / 会话 cookie** | **不做**。即使对方同意给，也不是证明越权的正确方式——会变成"接管他人会话"，法律性质完全不同。**贴出来的 cookie 立即视为已泄漏，要求吊销。** |
| 绕过认证 / SQLi 之类"拿到访问" | **不做**。无凭据时的任何访问都必须走绕过，而绕过本身即构成犯罪行为，与是否授权无关。 |
| 批量枚举 / 批量下载 | **不做**。PoC 是"结构 + 一条记录"，不是数据集。批量是数据泄露，不是漏洞证明。 |
| **并发 / 压力测试** | **不做**，除非书面授权明确写到可做 DoS 测试为止。单请求能证明"占用大量资源"，不能证明"打垮服务"。 |
| 在 GitHub 等公开平台提交 | **不做**。见下。 |

### 关于证据与版本控制

评估产物里通常混着三类东西，**分开处置**：

| 类别 | 例子 | 去向 |
|---|---|---|
| 方法论 | 本文 | 可脱敏后进公开仓库 |
| 结论 | 漏洞清单、复现步骤、未公开配置 | **不进任何远端**，按合同约定交付 |
| 第三方数据与源码 | 目标的前端 bundle、后端源码、业务数据样本 | **本机留存，用完删除，永不提交** |

推公开仓库前必须逐项确认：

- 有没有真实凭据（token / cookie / `sub` / `jti` / client_id）
- 有没有生产环境域名、内网地址、内部主机名
- 有没有未公开的漏洞细节——**尤其当某条发现本身就是"源码可被匿名下载"时，把源码再分发一次等于扩大该漏洞的危害**
- 有没有大体积业务数据（含人口、经济、地理参数）

加一条 `.gitignore`，并**在提交前用 `git status` 确认暂存区里只有该提交的东西**。大文件一旦进了历史就很难干净移除。

## 9. 常见误判清单

评估这类系统时，下面这些几乎每次都会出现，但多数**不是**漏洞。列出来是为了避免浪费时间：

- SPA 无路由守卫 / 菜单不过滤 → 不是漏洞（前端从来不是安全边界）
- `token_endpoint_auth_methods_supported` 含 `none` → 正确配置（公共客户端就该这样）
- 反射 Origin 但不带 ACAC → 不是漏洞
- 静态资源 cookie 缺 `Secure` → 低危，且该考虑的是直接去掉这个 cookie
- OIDC 回调 URL 看起来"可构造" → 先看有没有可控参数，静态回调路径不是开放重定向
- 公式/表达式功能存在 → 查求值器实现；手写递归下降 + 函数白名单 + `hasOwnProperty` 变量查找 = 不可注入
- `postMessage` 调用点存在 → 查 `origin` 校验，通常全是库内部逻辑
- bundle 里出现内网地址 → 先验证可达性与鉴权
- 体积很大的第三方库 → 查是不是误当成业务代码

反过来，**这些容易漏**：

- 集合端点无分页（§5.5）
- 本地代理的跨源无认证端点（§6）
- 开放注册把"需要账号才能触发"的问题降级为低门槛（影响定级）
- `Origin: null`（很多 CORS 检查只测了正常 Origin）
- 落盘文件截断导致的误判（§5.6）
