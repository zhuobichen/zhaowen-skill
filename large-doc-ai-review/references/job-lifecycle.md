# 任务生命周期：进程锁、心跳与状态

## 为什么不用数据库

源项目所有状态落在本地 `tmp/` 目录，**不用数据库、不用外部任务队列**。这不是偷懒，是刻意的：

- 单机部署，文件锁够用
- 状态天然带完整过程产物（中间 JSON、日志、原始响应），数据库反而存不下
- 排查问题直接看目录，不用查表

**代价：只能单实例单 worker。** 这是明确的取舍，别上多副本。

## 产物目录约定

```text
tmp/<业务>/<任务标识>/
|-- process.lock        # 进程锁（含 runId）
|-- heartbeat.json      # 心跳，每 15 秒刷新
|-- status.jsonl        # 状态追加
|-- run.log             # 事件日志
|-- input/              # 上传的原始文件
|-- steps/              # 各阶段中间产物
|-- output.json         # 最终结果
`-- error.json          # 失败时的详细错误
```

每个阶段都落盘中间产物。好处：LLM 输出、目录树、证据窗口都能事后复查，不用重跑。

## 状态机

```text
accepted -> parsing -> outlining -> locating -> reviewing -> assembling -> succeeded
                                                                  \-> failed
```

每次状态变化追加到 `status.jsonl`，不覆盖历史。

查询时的判定顺序（**顺序不能乱**）：

```text
1. output.json 存在        -> 直接返回成功结果
2. error.json 存在         -> 返回失败
3. 锁是陈旧的（超 180 秒） -> 返回失败（可被新提交接管）
4. 有"已启动"标记          -> 返回处理中
5. 什么都没有              -> 返回未找到
```

先看结果再看锁，这样"任务已完成但进程没清理干净"不会误报成失败。

## 进程锁

同一标识不允许并发提交。锁要做三件事：

1. **写入 runId** —— 每次运行生成新 id
2. **所有权双重校验** —— runId + 锁文件 inode 都要匹配才算持有
3. **持有者绑定到执行上下文** —— 提交和后台执行都绑定所有权上下文，子协程和 `asyncio.to_thread`
   继承这个上下文

为什么要这么严：**锁被接管后的旧运行不能释放新锁、不能更新产物。** 否则会出现两个运行同时写一个
任务目录，A 的结果被 B 覆盖，或者 A 把 B 的锁删了。

保护范围要包含任务目录**之外**的共享产物（比如年度指南文件、跨任务的汇总文件）。只锁任务目录是不够
的。

运行 ID 写进所有产物，产物写入时校验："我是当前 run 吗？"不是就拒绝写。

## 心跳

运行期间每 15 秒刷新 `heartbeat.json`。

- 心跳超过 180 秒不动 -> 锁视为陈旧
- **心跳失败不能发布成功结果** —— 这条很重要。心跳挂了说明这个 run 可能已经不被承认了，这时写出
  的结果可能是陈旧 run 的

不同标识的任务用 `BackgroundJobConfig` 显式提供各自的心跳，不要求请求里有统一的 ID 字段。

## 并发与取消

```text
共享并发助手：任一子任务失败 -> 取消其余兄弟任务 -> 等它们清理完 -> 再抛原异常
```

不等待就抛异常会留下悬挂协程，继续写产物、继续占资源。

互斥区**不能跨越 `await`**。持锁期间 await 会让出事件循环，别的协程可能进临界区把状态改坏。

重复取消时要先 drain 清理再释放锁。取消必须继续向调用方传播，不要吞掉。

## 服务重启

- 已有 `output.json` 的任务**仍可查询**
- 未完成的任务**不会自动续跑** —— 这是有意的，避免重启后状态错乱

所以前端/调用方要处理"任务卡在中间态"的情况：提示用户重新提交，而不是无限轮询。

## API 侧

**提交和查询分离**：

```text
POST /v1/applies/formalreview          -> 立即返回受理（不等待）
GET  /v1/applies/formalreview/{uuid}/result  -> 轮询
```

受理阶段如果锁冲突，返回 HTTP 409。

调用方不能覆盖模型、`maxChars`、`saveProcessData` 这类服务级配置，统一由服务端控制。这防止调用方
把服务调成慢模式或关掉过程记录。

## CI 门禁

源项目把并发和锁的语义写进了工程门禁，改动时必须保持：

- 进程锁记录 `runId`，所有权用 runId + inode 双重校验
- 被接管的旧 run 的产物写入必须失败
- `PROCESS_OWNERSHIP_GUARD` 不能跨越 `await`
- 后台任务统一用 `run_background_job()` 管状态、心跳、资源清理；业务钩子只管自己的结果，不要重复
  写生命周期状态
