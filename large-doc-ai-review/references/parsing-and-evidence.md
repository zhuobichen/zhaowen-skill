# 分层解析与证据链

## 为什么不能直接让 LLM 读全文

几百页 PDF 的问题不是"模型读不完"，而是**读完也没有定位**。模型给你一段总结，你无法回答
"这条结论出自第几页"。审核系统必须让每个结论都能回溯到具体页码和章节，否则人工复核无从下手。

所以架构必须拆成"定位"和"判断"两层：

```text
定位层（确定性，代码 + 少量 LLM）：整本 -> 块 -> 目录树 -> 证据窗口
判断层（语义，LLM）：单个证据窗口 -> 结论 + 理由
```

## 第 1 层：PDF -> 带页码的块

用现成服务，别自己写 OCR。选型参考：

- **MinerU** —— 中文文档效果好，输出块类型 + 坐标，适合国内申报/公文类材料
- **unstructure** —— 通用，英文文档好
- **PyMuPDF + 版面分析** —— 纯 Python、无外部依赖、快，适合电子版 PDF（扫描件不行）

每块至少保留：

```json
{
  "blockId": 142,
  "page": 17,
  "type": "table",
  "text": "原始文本...",
  "bbox": [0.12, 0.30, 0.91, 0.48]
}
```

`blockId` 是全局递增的稳定索引，后面所有定位都靠它。`type` 区分段落/表格/标题/图注。

**注意**：`page` 一定要留。人工复核时第一个动作就是翻到那一页。

## 第 2 层：预处理

解析结果直接喂给 LLM 会有噪声。必做：

- 去页眉页脚（每页顶部/底部重复出现的短行，用出现频次阈值判定）
- 合并被 PDF 切碎的换行（中文按标点+长度判断，英文按空格+连字符）
- 全角半角、不可见字符、多余空白的规范化
- 表格转成 Markdown 或结构化行列，别留纯文本

**保留原始文本**。预处理后的文本用于定位，原始 `text` 用于送 LLM 判断——OCR 有误差时，模型看
原文比看清洗后的抽取字段更靠谱。

## 第 3 层：目录树（系统的骨架）

让 LLM 输出章节层级 + 每节的块索引范围：

```json
{
  "outline": [
    {
      "title": "二、研究内容与技术路线",
      "level": 1,
      "startBlock": 210,
      "endBlock": 356,
      "children": [
        { "title": "2.1 总体思路", "level": 2, "startBlock": 215, "endBlock": 248 }
      ]
    }
  ]
}
```

这一层最容易出错，所以设计成**可重生成**：

1. 首次生成
2. 代码校验：块索引是否越界、层级是否断裂、区间是否重叠/留空洞、覆盖率是否够
3. 校验不过或覆盖率不足 -> 带错误信息重生成（最多 N 次）
4. 还不过 -> 降级为"按页窗口切分"，走无目录的兜底路径

**不要因为目录生成失败就整份任务失败。** 必须有降级路径。

配套通常还要几个小步骤：候选标题发现、标题合并、标题识别、拆分、缺口审计。可以简化，但要保留
"缺口审计"——检查有没有章节在目录里缺失。

## 第 4 层：投影定位（纯代码）

把目录树投影回原文块，得到每节的证据窗口：

```python
def project_outline(blocks, outline):
    windows = []
    for node in flatten(outline):
        window = blocks[node["startBlock"] : node["endBlock"] + 1]
        windows.append({
            "sectionPath": node["titlePath"],   # ["二、研究内容", "2.1 总体思路"]
            "pages": sorted({b["page"] for b in window}),
            "blocks": window,
        })
    return windows
```

这步**必须是确定性代码**，不要让 LLM 参与。理由：可复现、可测试、不消耗 token、不会幻觉。

## 第 5 层：证据传递

判断层拿到的不应该是"结论 + 理由"，而是**原始证据文本**。

优先级顺序（这条很重要）：

1. 原始 `text`（模型自己读）
2. 代码抽取的结构化字段（表格行列、定位到的章节号）
3. 目录元信息（章节路径、页码范围）

**代码抽取的字段是辅助和调试证据，不是唯一真相。** 常见错误是：代码只抽了字段名和值就送给模型，
模型看不到上下文，于是判断错。正确做法是字段 + 原文一起给。

一次请求的输入应该是：

```json
{
  "sectionPath": ["三、项目预算", "3.2 设备费"],
  "pages": [42, 43, 44],
  "documentText": "<原始文本全文>",
  "extractedFields": { "<代码抽的字段>": "..." },
  "criteria": "<来自 _spec.json / prompt 的判断标准>"
}
```

## 证据的对外格式

结论里的 `sourceInfo` 只允许：

```json
{ "pages": [42, 43], "materialTitle": "项目预算表", "sectionTitle": "3.2 设备费" }
```

**不要输出行号。** 行号会因为重新解析、PDF 版本、排版差异而漂移，一旦漂移人工复核就会指错地方，
系统可信度直接归零。

## 复用建议

`data/` 目录可以预先存好**已解析好的规则文件**（如年度申报指南、政策文件）成本地 JSON，运行时查表
比对，不用每次调 LLM。这类文件一年变一次，缓存下来能省掉大量成本。
