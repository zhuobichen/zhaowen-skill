# 大文件 AI 审核工程范式

面向这类任务：**几百页 PDF 丢进去，输出带证据定位的逐项审核结论**，而不是让模型读完整本再
"总结一下"。

## 一句话架构

```text
上传 -> 解析成带页码的块 -> 生成目录树 -> 目录投影回原文定位证据窗口
     -> 按窗口逐块调 LLM 做语义判断 -> 代码校验与兜底 -> 装配带页码的结论
```

**核心是把"找内容"和"下判断"分开**：定位交给目录树 + 代码，语义判断才交给 LLM。这样每一页都有
页码证据，每个结论都能回溯，LLM 挂了也能降级而不是整份失败。

## 六条铁律

违反其中任何一条，大文件审核都会在真实数据上崩。

1. **绝不把整份文档塞进上下文。** 先切块、先定位，LLM 每次只看一个证据窗口。
2. **结论必须带证据定位。** 只输出 `页码 + 材料/章节标题`，不输出行号（行号随排版漂移，不可复现）。
3. **Prompt 业务规则不许写进 Python。** `.md` 放业务判断规则（给模型看），`_spec.json` 放字段
   schema 和枚举（给代码校验），Python 只负责加载、校验、兜底。见 `references/prompt-contract.md`。
4. **结论字段必须写在证据字段之后。** 见下方"强制检查"。
5. **LLM 失败必须有代码兜底。** 跳过、报错、返回非法 JSON 三种情况都要有确定的降级路径，且降级
   结果要保留足够证据让人工复核。
6. **"没找到" 不等于 "不合格"。** 签字、印章、证照真伪这类**不允许**自动判定；自动定位失败只能
   记为"不确定"并转人工。见 `references/verdict-and-fallback.md`。

## 最小骨架

```text
app/
|-- parsing_core/            # 与业务无关的底座，一个项目只建一次
|   |-- preprocessing.py      # 去页眉页脚、拆行、文本规范化
|   |-- outline.py            # 目录树生成与校正
|   |-- prompt_runner.py      # 加载 .md + _spec.json -> 调 LLM -> schema 校验
|   |-- llm_pool.py           # 并发限流 + 有界重试
|   `-- background_job.py     # 进程锁 + 心跳 + 状态机
`-- <业务包>/                 # 一种审核任务一个包
    |-- pipeline.py           # 编排
    |-- prompts.py            # 只做参数拼装，不含业务规则
    `-- prompt_templates/
        |-- <check>.md           # 业务判断规则 + JSON 输出示例
        `-- <check>_spec.json    # promptFile + properties + required + enum
```

**业务包之间不共享业务逻辑，只共享 `parsing_core`。** 材料差异留在各自的 prompt/spec 里，不要塞进
通用代码。

## 实施顺序

1. **先定结论词表。** 决定有几档结论、每档的确切含义、整体结论怎么聚合（通常是"最严重的一档
   胜出"）。这一步不定，后面全是返工。
2. **搭解析层。** PDF -> 带页码/类型/坐标的块。直接用现成服务（MinerU、unstructured、
   PyMuPDF + 版面分析），别自己从头写 OCR。
3. **生成目录树。** 让 LLM 输出章节层级 + 每节起止块索引，代码再校验（块索引越界、层级断裂、
   覆盖不全）。目录是这个系统的骨架，错了后面全错，所以要**允许重生成**。
4. **投影定位。** 目录 -> 原文块区间，得到证据窗口。这步纯代码，确定性执行。
5. **写 prompt + spec。** 一个审查点一对文件。见 `references/prompt-contract.md`。
6. **写校验与兜底。** schema 校验、必填检查、枚举归一、覆盖完整性检查。
7. **挂任务生命周期。** 进程锁 + 心跳 + 状态文件。见 `references/job-lifecycle.md`。
8. **接 CI。** 至少两个门禁：prompt 契约字段顺序 + 样例数据全流程。

## 强制检查

Prompt 的 JSON 输出示例是**按生成顺序**写的。如果 `result` 写在 `reason` 前面，模型会先定结论
再补理由，产出"结论说 FAIL、理由说符合"这种自相矛盾的结果。真实项目里踩过这个坑。

```bash
python scripts/check_verdict_order.py <你的 prompt 目录>
```

退出码 1 即为违规。这个脚本已在 227 个真实 prompt/spec 文件上验证过零误报。

## 工程约束（照抄能省两周）

- **LLM 并发要有上限**（全局 + 单请求双层），并做**有界重试**，不能无限重试烧钱。
- **超时给足**（1800 秒级），大文件单次请求可能跑很久。
- **单实例单 worker**：状态存本地文件、锁是本地文件锁，就别上多副本。
- **类型门禁只许缩小不许扩大**：baseline 里已有的问题可以留，新增的必须修。
- **示例数据必须合成**：文档、prompt、测试里的姓名单位编号金额都要用假值，格式长度对齐真实
  合同（`SQ2099AAA000001` 这种），别用 `xxx` 破坏机器校验。
- **Windows 下读中文文件要显式 `-Encoding UTF8`**，否则会误判成乱码。
