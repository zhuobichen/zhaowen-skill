# 本机活动痕迹与远程访问检查

回答一类问题：**在我不知道的时候，这台电脑有没有被人用过 / 被人连进来过。**

## 一键流程

```bash
# 1) 采集（需要管理员权限才能读安全日志）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/collect.ps1

# 2) 分析 + 生成 HTML（默认写到桌面 activity_report.html）
python scripts/analyze.py

# 3) 若第 2 步查出「有人在远程控制软件里连进来过」→ 看每次会话到底做了什么
python scripts/session_detail.py
```

**默认窗口 = 最近两天（昨天 + 今天）。** 改窗口：

```bash
python scripts/analyze.py --days 7                       # 最近 7 天
python scripts/analyze.py --from 2026-09-30 --to 2026-10-01   # 指定区间（覆盖 --days）
python scripts/analyze.py --work <采集目录> --out <报告路径>
```

两个脚本通过 `%TEMP%\activity_forensics` 传数据；`collect.ps1 -Out X` 与 `analyze.py --work X` 必须一致。

## 报告结构（12 节）

1. 结论卡片（远程桌面 / 远程登录 / 交互式登录 / 自启动 / **运行次数是否可得** / 能否区分是谁）
2. 日期聚焦：逐小时热力图 + 事件序列 + 浏览器 + 时间线 + 回收站 + 下载 + **远程控制方向**
3. 查不到什么（先看这节再信结论）
4. 事件时间线（开机/登录/程序运行/计划任务同轴）
5. 程序最后运行时间（Prefetch + UserAssist 双源互证）
6. QQ 聊天窗口活动（`fuin=<QQ号>` 痕迹）
7. 登录与远程访问（按登录类型拆分）
8. 账号与本地数据 + 已安装软件 + 系统错误事件
9. 自启动来源复查（Run 键/启动文件夹/Winlogon/服务，**每次实测**）
10. 相关二进制数字签名
11. 建议
12. 附录（原始数据）

## 证据源：能证明什么、不能证明什么

| 源 | 能回答 | 硬限制 |
|---|---|---|
| Prefetch `*.pf` mtime | 程序**最后一次**何时运行 | 只保留最后一次；上限 1024 条；只覆盖系统盘 |
| UserAssist | 由**用户界面**发起过哪些启动 | 只记 UI 启动；自动启动不写这里 |
| 安全日志 4624 | 有没有远程(RDP)登录 | 需 4624 审计；只能区分登录类型，不能区分人 |
| 安全日志 4688 | 精确启动时间 + 父进程 + 发起账户 | **默认关闭**，多半查不到 |
| 计划任务 LastRunTime | 自动化启动的精确时刻 | 只覆盖计划任务 |
| 浏览器历史 | **人明显在电脑前**的时段 | 只覆盖有历史库的浏览器 |
| 回收站 `$I` | 什么时候删了什么 | 清空回收站会一并抹掉 |
| 远程控制软件日志 | **有没有人连进来**、连进来后动了什么 | 保留期短（ToDesk 约一周） |

**唯一的黄金交叉**：把"程序运行时刻"和"浏览器访问时刻"并排看。两者同时活跃 = 有人在操作；只有程序在跑、浏览器静默 = 可能是自动化或后台。

## 陷阱（每一条都实际踩过，且都是静默出错）

### 1. 时间基准换算 —— 最容易把"有"变成"没有"
一次排查里连踩三种，全都是**静默的**（不报错，只是少数据）：

- **Chromium 时间戳**（Edge/Chrome History 的 `visit_time`）= 1601-01-01 起的**微秒**，且基准是 **UTC**。
  两个独立的坑：
  - `(dt - datetime(1601,1,1)).total_seconds()` **已经含**了 1601→1970 的偏移，
    再加 `11644473600` 会偏 **369 年** → 查询 0 条 → 看起来像"那天没上网"。
  - `dt` 是**本地裸时间**而时间戳是 **UTC**，只做减法会整体偏一个时区（UTC+8 上偏 8 小时）→
    **每天 00:00–08:00 被漏掉，且窗口末尾多算次日**。
  - 正确的一对：`fromtimestamp(v/1e6 - 11644473600)` ↔ `int((d.timestamp() + 11644473600) * 1e6)`。
- **FILETIME**（UserAssist / 回收站 `$I` / Prefetch 内嵌）同样是 UTC。
  `datetime(1601,1,1)+timedelta(...)` 得到裸 UTC，与 `os.path.getmtime`（本地）混用差一个时区。
  统一走 `datetime.fromtimestamp(v/1e7 - 11644473600)`。

**防回归**：`analyze.py` 启动时会跑 `_check_timebase()` —— 让两个函数在几个时间点上**往返自测**，
不互逆就直接 `SystemExit` 并打印偏移量。**任何一对"编码/解码"函数都该这样自测**，
因为这类错误的唯一症状是"数据变少"，而"变少"看起来永远像"本来就没有"。

### 2. Prefetch 新格式
Windows 11 24H2+ 的 `.pf` 头是 `4d 41 4d 04`（"MAM"），不是老的 `53434341`（"SCCA"）。
老解析器和网上的 prefetch 解析工具**都读不出**"最近 8 次运行时间"。此时只能退回用**文件 mtime**，
并如实说明拿不到运行次数。

### 3. UserAssist 运行次数多半取不到
不少 Win11 版本里计数字段恒为 0。**别直接报 0**：先统计所有记录的该字段最大值，
若最大值只有个位数（连 `csrss.exe` 都同量级），说明这个版本不落盘次数，报告里要写"取不到"。
另外 `winreg.EnumValue` 遇到读不了的值会抛 `OSError`；**只有 `winerror==259` 才是"枚举结束"**，
其他错误必须 `i += 1; continue`，否则会静默丢掉后面所有条目。

### 4. 回收站 `$I` 的偏移
版本 2（Win10+）布局：`0-7` 版本、`8-15` 原大小、`16-23` 删除时间、**`24-27` 路径长度**、**`28-` 路径**。
按 24 读路径会整体错位 4 字节，所有文件名变成一个乱码字符 —— 看着像"文件名很奇怪"，实际是偏移错了。

### 5. 远程控制软件的方向 —— 搞反结论就反了
ToDesk 日志里两种行几乎一模一样，`myid`/`destid` 也相同：
```
client recv connect request, myid=<本机>  → 本机主动连出去
host   recv connect request, myid=<本机>  → 本机是被控端，有人连进来了
```
辅助判据：`client` 带 `mode_=1`，`host` 带 `mode_=0` 且随后出现
`TCP_VIDEO_HOST begin connect transfer server`，并拉起一个 `session` 进程。
**必须按 `host`/`client` 分开统计**，不要把所有 `connect request` 混成一个数。

### 6. 域名统计要排除非 http 目标
`url.split('/')[2]` 对 `chrome-extension://<32位随机id>/...` 会取到扩展 ID，
在"访问最多的站点"里显示成一串可疑随机域名 —— 实际只是新标签页扩展。只统计 `http(s)://`。

### 7. 取证过程会污染证据
脚本自己（python/bash/powershell，用无头浏览器渲染 HTML 时还有 msedge）会在
Prefetch 里留下新记录，可能覆盖掉你要看的"最后一次运行"。
**报告里必须写明这一点**，并让用户忽略取证开始之后的、属于工具自身的记录。
用独立的 `--user-data-dir` 跑无头浏览器可避免污染浏览器历史（走另一个 profile），但**挡不住 Prefetch**。

### 8. "没搜到"不等于"不存在"
搜索范围被 `-Depth` / `head` 截断过，会得到假的否定结论。定位二进制/宿主时，
先确认搜索真的覆盖到了目标目录，再下"没有"的结论。

### 9. 服务日志只说明"连上了"，不说明"做了什么"
`host recv connect request` 只证明会话被建立。**他连进来之后动了什么**，只存在于
每次会话拉起的 `<sessionXXXX>_YYYY_MM_DD.log` 里：

```
session send <帧数> frame, recv <字节> mouse <鼠标事件> key <按键> text <文本>
```

`mouse / key / text` 是从对端收到的输入计数，**只增不减** —— 因此「长时间停在同一个值」
就等于那段时间没人操作。用 `scripts/session_detail.py` 直接生成这条时间线。

两种典型形态：
- **有鼠标、无键盘**：对方在看/点，没打字。可能是自己远程看自己的机器。
- **鼠标键盘都持续增长**：对方在真的操作这台机器。

同时检查有无录制与文件传输产物（`*.mp4` / `*.tos`、`%USERPROFILE%\Downloads\ToDesk`）。

## 解读要点

- **只有 18:00 之后、凌晨、工作日上班时间**这些时段的活动才值得追问 —— 先问用户那段时间在不在。
- **同一个 Windows 账户下无法区分操作人**。要区分必须另建账户。报告里必须直说。
- **"程序被运行"≠"有人操作"**：先看自启动清单（第 9 节），把自动化解释掉再谈人为。
  例：鲁大师的 `LdsMultiWechatA` 会在每次登录后 1 分钟自动拉起微信多开。
- 两个独立来源（Prefetch vs UserAssist）对同一程序的时间要**并排比对**；
  差值接近整小时的整数倍 = 时区错。脚本已内置该自检。

## 局限（写进报告，不要省略）

- Prefetch 只有"最后一次"，**没有次数**——"某天没出现"不等于那天没跑。
- 4688 默认关闭 → 没有"谁启动的"。
- 时间线（ActivitiesCache）在很多机器上未在收集，**不能用来反证"没人用过"**。
- 回收站被清空 = 证据一并消失，**不能反证"没删过"**。
- 远程控制软件日志保留期短，只对保留期内成立。
- 所有文件系统/注册表时间戳都可能被有管理员权限的人改写；本地自检不是取证级证据。
