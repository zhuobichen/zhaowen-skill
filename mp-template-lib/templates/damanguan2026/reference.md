# 人工复核结果（2026-10-10）

复核方法：读 `sample.html` 原始标签 → 对整页截图做**像素统计**（看高饱和像素的冷暖是否对称）
→ 定点裁图放大到全分辨率人眼确认。

## 结论一：这个模板几乎没有样式 —— 全是「黑字 + 粗体」

- `color:` 全篇只有 4 种取值：`rgba(0, 0, 0, 0.9)`×135、`rgb(255, 255, 255)`×4、
  `initial`×4、`rgb(15, 17, 21)`×1。**没有任何彩色。**
- `text-decoration: underline` 出现 **0 次**，`border` 声明 **0 处**，无圆角、无阴影、无卡片。
- 唯一的强调手段是 **`<strong>` 粗体 ×40**（另有 `<em>`×3，但样式写着 `font-style: normal`，等于无效）。
- 正文 `17px / line-height: 1.6 / letter-spacing: 0.034em`。

## 结论二：`accent_text: 133` 是**误报**，真实的强调色文字是 0

判据是：

```python
n_acc = len(re.findall(r'<(?:strong|span)[^>]*color:\s*(?:rgb|#)[^;"]{3,30}', html, re.I))
```

它命中的 133 处，颜色取值实测如下：

| 颜色 | 处数 |
|---|---|
| `rgba(0, 0, 0, 0.9)` | **132** |
| `rgb(15, 17, 21)`（近黑） | 1 |

**132/133 是纯黑。** 两个原因：

1. 分支里的 `rgb` **会匹配上 `rgba(` 的开头**（`rgba` 以 `rgb` 开头，后面是 `a`，正则不设边界）；
2. 更根本的：这个判据**从头到尾没有检验过颜色是不是彩色**，只看有没有 `color: rgb…` 这个语法。

所以这个模板报的「强调色文字 133 处」，实际是「有 133 个 span 写了 color 声明」，
与「强调色」无关。⚠️ **库里的 `accent_text` 计数都可能被同样地抬高**，别的模板要不要信得逐个复核。

## 结论三：`mp_article: 2` 名字、含义、数量三样都错

```
<mpcpc class="js_cpc_area res_iframe cpc_iframe" ... src="/cgi-bin/readtemplate?t=tmpl/cpc_tmpl#..." style="display: none;">
```

`<mpcpc>` ×2 实测：class 含 `js_cpc_area / cpc_iframe`、`style` 含 `display:none`
—— 这是**微信的 CPC 广告位**，属于平台家具，不该当模板构件。
检测器 `MP_KINDS` 里把它登记成 `('mp_article', '文章链接卡片')`，**名字和实物对不上**。

而这篇**真正的**文章链接是：

```html
<a class="normal_text_link mp_article_text_link" ... textvalue="《量子杂志》：80年后，数学家…">
```

共 **3 条**（都在文末「相关链接：」后面），检测器**一条都没认出来**。
于是 `mp_article: 2` 这个数字：名字不是文章链接、实物是广告位、数量(2) 也不是真链接数(3)。

## 结论四：`font_families` 的 `mp-quote, &quot` 是缺陷 #13 现形

```
font_families: ["mp-quote, &quot" x132, "\&quot" x3, "quote-cjk-patch, Inter, system-ui, …" x1]
```

前两项是被截断的残渣 —— `decl()` 的 `([^;]+)` 遇到 HTML 实体 `&quot;` 里的分号就停了，
真实字体栈是 `mp-quote, "PingFang SC", system-ui, -apple-system, …`。
SKILL.md 缺陷 #13 一直挂账，注释写着「下次谁再用 `decl()` 去解析 URL 或字体名就会踩」
—— **就是这一次**。本模板的 `font_families` 不要采信。

## 结论五：我自己在复核前看错了颜色（留档）

第一遍我只看缩略图，断言正文有「砖红 / 青绿两种下划线强调」。**是错的**。
像素统计戳穿了它：

| 检查 | 结果 |
|---|---|
| 偏暖像素（红 > 蓝+12） | 24595 |
| 偏冷像素（蓝 > 红+12） | 25385 |
| 色值档位 | `(63,31,31)`/`(183,111,31)` 与 `(31,31,63)`/`(31,103,183)` **成对互补** |

**冷暖数量近似相等、色值成对互补、档位是 31/63/111/159/191/231/255**
—— 这是浏览器**次像素抗锯齿（ClearType）**在细笔画两侧留下的色边，
不是真彩色。缩图（LANCZOS 到 760px）又把这些色边糊成了「下一行的下划线」。

> 教训和库里那条「反推样式：数值对≠结构对」同源：**颜色也要用离散量判，别用眼睛判**。
> 这次判据是「冷暖像素数是否对称 + 色值是否成对互补」。
> 另外，第一次整图统计还给出了 4.86% 的高饱和像素 —— 那**全是图片区贡献的**，
> 说明统计必须**先划定区域**（纯正文带）再看，否则会被配图污染。

## 对「这个模板值不值得收」的说明

它**几乎没有可复刻的样式**：没有颜色、没有装饰、没有构件，本质是「微信默认正文 + 粗体」。
它的价值不在版式，而在于：① 给出「不做任何装饰」这个基线长什么样；
