# 公众号模板库

把「看到一个好排版」变成「能吃进来的可复用主题」。

## 核心工具：`scripts/extract_theme.py`

```bash
# 从已发表文章 URL（用 browser-act 免登录打开，公开文章不用扫码）
python scripts/extract_theme.py --url "https://mp.weixin.qq.com/s/xxx" --name redcard2026

# 从本地 HTML（整页或只给正文片段都行）
python scripts/extract_theme.py --html ./body.html --name xxx --preview ./shot.png
```

产出 `templates/<name>/`：

| 文件 | 内容 |
|---|---|
| `theme.json` | 设计令牌（配色/字体/字号/行高/圆角/阴影/间距）+ 组件形态，机器可读 |
| `reference.md` | 人读的反推记录 + **人工复核清单** |
| `sample.html` | 抠下来的正文 HTML，对照用 |
| `preview.png` | 渲染截图 —— **最重要的对照物** |

## ⚠️ 这个 skill 存在的理由：数值对 ≠ 模板对

2026-09-30 实测踩到的坑：反推一个红色卡片模板，**颜色、圆角、字号、阴影全部解析正确**，
但结构错三处 ——

| 解析出来的 | 实际 | 
|---|---|
| 章节标题条 = 左标签 + 右胶囊（两端布局） | **红方块 + 英文小字 + 中文标题**（三件套） |
| 引用块 = 圆角浅底 | 还多一根 **`border-left` 红竖线** |
| 胶囊 = 纯文字 | 内嵌一个 **6px 小红圆点** |

**三条都不是「数值差一点」，是「少了个元素」。数值可以推理，缺元素只能看。**

所以：**`theme.json` 永远不足以还原模板，必须打开 `preview.png` 人眼对照。**
`reference.md` 里那份「人工复核清单」就是为此存在的，别跳。

### 两个已修的识别 bug（同类错误的模板）

1. **只在 `<section>` 里找组件** → 胶囊、圆形序号常挂在 `<span>` 上，会**整类漏掉**。
   已改为 `where='both'`。
2. **用「线宽 ≥2px」区分标题条和行内高亮** → 实测里标题条 3px、高亮 2px，
   但两者本来就不该靠粗细分。**靠挂载位置**（section vs span）才是稳的判据。

> 教训：判据要选**语义上必然不同**的那个维度。粗细、颜色这类连续量容易重叠；
> 挂载位置、标签类型这类离散量不会。

## 已修的缺陷（每一条都是实测撞出来的）

### 1. 只在 `<section>` 里找组件 → 整类漏
胶囊、圆形序号常挂在 `<span>` 上。已改为 `where='both'`。

### 2. 用「线宽 ≥2px」区分标题条和行内高亮 → 判据选错
实测标题条 3px、行内高亮 2px，但**两者本来就不该靠粗细分**。
改用**挂载位置**（section 上是标题条、span 上是高亮）。

> 教训：判据要选**语义上必然不同**的维度。粗细、颜色这类**连续量**容易重叠；
> 挂载位置、标签类型这类**离散量**不会。

### 3. 组件签名只覆盖「见过的模板」→ 新模板整类漏 ⭐ 最重要
签名（卡片/标题条/分隔线…）都是从第一个模板总结的。反推第二个（灰调极简）时，
它是双圆点列表 + 1px 描边盒 + 深色块，**签名一个都不匹配**，只认出 3 项。

修法不是「再多猜几个签名」—— 而是 output 里增加一节 **`structure`（结构事实）**：
标签普查、所有 border / background / display declaration、小尺寸元素。
这些是**事实**，不会因为我没猜到就漏。

> 教训：**用「事实枚举」兜底「模式识别」**。模式识别必然有覆盖边界，
> 而边界外的东西不会报错、只会静默消失。加一层不依赖任何假设的原始事实，就兜住了。

### 4. 以为「标题条 = 下划线式」→ 漏掉底色式
第一个模板的章节头是 `border-bottom: 3px solid`（下划线式），我就只按这个写签名。
第二个模板的章节头是 `background:#222222; color:#FFF; text-align:center`（**底色式**），
一点 border 都没有 —— 整类漏掉。这条是**人工复核**时抓到、不是脚本自己发现的。

已补 `filled_label` 签名：实色底 + 内边距 + (大字号 or 居中)。

> 教训：**同一个语义位置可能有多种实现手法**。别把「第一个样本的做法」当成该类别的定义。
> 判断「这是不是标题条」应该看**它在这个位置起什么作用**（承接上下文的分段）而不是
> 「它有没有某个具体属性」。脚本做不到这层语义，所以人工复核那一步不能省。

### 5. 分隔线只认「渐变 + 1px」→ 漏掉纯色 2px
第三篇用的是 `background-color: rgba(163,236,66,0.19); height: 2px` —— 纯色、2px、无渐变，
按当时的签名整类认不出（实测 49 处）。已补 `thin_bar`（高 ≤4px + 有底色）。

### 6. 差点把 60 个空 SVG 当成装饰件统计 ⭐
第三篇有 60 个 `<svg>`，看着像"用了 60 个 SVG 图标"。**实际全是微信编辑器的空占位符**：

```html
<svg viewBox="0 0 1 1" style="width:0" role="img" aria-label="插图"></svg>
```

`width:0`、无内容、60 个完全相同。**这条是"先看再改"救回来的** ——
当时正准备加 `svg` 检测器，先去看了原始 HTML，才发现加它是错的。

已改为 `svg_real`：先滤掉 `width:0` 的，第四篇验证有效（40 个 → 滤掉 27 → **13 个真的**，
与 `<g>` 标签数 13 吻合；截图里那个圆形纹章就是其中之一）。

> 教训：**加检测器之前先看它到底长什么样**。统计一个标签类型的出现次数很容易，
> 但「这个标签在这里是什么」是另一回事。不先看一眼，就会把一个纯噪声项
> 当成有意义的指标写进产物 —— 而且它**看起来特别像真的**。

### 7. `<mp*>` 不能笼统数 —— 一类标签里混着真组件和空标记
第五篇（新闻体）有 3 个 `<mp*>`。笼统数会得出「3 个嵌入组件」，**错的**。
逐个看实际标签名才分得清：

| 实际标签 | 是什么 | 该不该计数 |
|---|---|---|
| `<mp-common-videosnap>` | 视频号视频卡片 | ✅ 该 |
| `<mp-common-profile>` | 公众号名片 | ✅ 该 |
| `<mp-style-type>` | 样式标记（`data-value="3"`，无内容） | ❌ 不该 |

已改为**按具体标签名分别识别**（`mp_video` / `mp_profile` / `mp_audio` /
`mp_miniprogram` / `mp_article`），剩下归到 `mp_other` 并注明「多为无意义标记」。

> 教训：**前缀相同的标签不一定是同一类东西。** 数一个前缀之前，先看看这个前缀下
> 到底有几种标签、各是什么。这条和 #6 是同一类错误 —— 都是「数得太粗」。

### 8. 新检测器和旧检测器覆盖重叠 → 同一批元素被数两遍
加 `thin_bar`（高≤4px + 有底色）之后，红色模板报出 `divider 13` **和** `thin_bar 13` ——
**两个数字完全相等，因为就是同一批元素**：它的分隔线是渐变式，而 `thin_bar` 不排除渐变，
所以两边都算了。

这条是**回归检查**抓到的（改完检测器后重跑旧模板、逐项对比计数）。
不跑这一步不会发现 —— 两个数各自看着都合理，只有并排看才会注意到它们相等。

已修：`thin_bar` 排除 `gradient(`，渐变式归 `divider`。

> 教训：**改检测器后必须重跑旧样本并逐项 diff。** 新增检测器最容易造成
> 「两个名字数同一批元素」，而这类错误在任何单个结果里都看不出来 ——
> 只有比对才现形。修完后 `divider 13 / thin_bar 无` 才正确。

### 9. 同一个号反复用同一个模板 → 会收到重复项
收第六篇时发现它和 `graylist2026` **字体、配色、字号完全一致** ——
是同一个号（道哥说AI）的同一套样式，只是这篇更长、多露出 4 类组件。
再做一遍反推 + 人工复核是纯浪费。

已加**指纹查重**：`fingerprint()` 取「字体 + 有彩色主色」（滤掉透明、黑白灰），
`find_duplicate()` 与已有模板比对；命中则：

- `theme.json` 写入 `duplicate_of: <已有名字>`
- 控制台明确报出「同款模板已存在」+ 依据 + 处置建议

**处置策略**：若新样本更长/组件更全，**用它替换旧样本**（本次就是这么做的：
`graylist2026` 从 8 类升到 12 类）；否则直接删掉本次产出。

> 教训：**"收到一个新 URL" ≠ "得到一个新模板"。** 公众号的版式是**按号固定**的，
> 不是按文章变的。所以收模板应该**按号取样**，而不是按链接 ——
> 同一个号收第二篇的边际价值，主要在于「样本更全」，不在于「又一个新样式」。

### 10. 章节标题的横线是**背景图** → 只看 CSS 数值永远看不见 ⭐
第六个模板（AI前线）的章节标题长这样：数字骑在一条线上，下面才是标题。

```html
<p style="font-size:20px; color:rgb(0,179,139);
          background-image:url(同一张图，4 处相同);
          background-position:left 28px; background-size:100% 6px">
  <span style="display:block; padding-left:22px; font-size:32px">1</span>
  <section><span style="color:rgb(0,179,139); font-size:20px">标题文字</span></section>
</p>
```

那条「绿粗线 + 小绿方块 + 浅灰长线」**整张是一幅栅格图**，被拉成 `100% × 6px` 贴上去。
它既不是 `border` 也不是 `background-color` —— 数值层面只是一句「一个 100%×6px 的
background-image」，不看图永远不知道那画的是一条线。而且标题不是 `h1~h4` 而是 `<p>`，
所以按标签统计也漏。

**这条是人工复核抓到的，靠扫像素**：先扫 `preview.png` 里的绿色像素拿到精确 y 坐标，
再按坐标裁图放大。比在缩略图上目测位置可靠得多 —— 我一开始目测切了两次都切偏了。

已加两个东西：
- `bgimg_rule`：`background-size` 是细长条（高 ≤ 8px）即视为「线」。判 size 不判
  `background` 简写 —— 简写里的 `cover`（真配图）不该算进来。
- `bgimg_any`：**兜底事实**，不判断用途，只数「有几个元素挂了背景图」。这是本文档
  第 3 条「用事实枚举兜底模式识别」的又一次应用。

### 11. `svg_real` 把 **4px 圆角补角料**当成装饰件
`<svg viewBox="0 0 2 2" width="4px" height="4px" class="border_filler border_filler_lefttop">`
—— 编辑器画边框时四角各塞一块。AI前线里报出「4 个真 SVG」看着像「用了 4 个图标」，
**实际全是这个**。只滤 `width:0` 不够。

已补判据：class 含 `border_filler`、或宽高 ≤ 6px、或 viewBox ≤ 4×4 → 排除。
判据用**离散**特征（尺寸、视框），不用颜色粗细那类连续量。

> 回归验证：autumn2026 的 `svg_real=13` **纹丝不动** —— 收紧过滤没误伤真 SVG。
> 这是收紧过滤器时最该担心的事，光看新模板的结果是看不出来的。

### 12. `count=0` 的项会被整条丢掉 → **过滤器的改动会静默** ⭐
`detect_components` 收尾是 `return {k: v for k, v in comps.items() if v.get('count')}`。
把 svg_real 从 4 滤成 0 之后，这一项**从产物里消失了** —— 读者分不清
「滤光了」和「检测器根本没跑」。是**改动后跑前后对比**才发现的：两版 diff 里它显示为
`4 -> (消失)`，而不是 `4 -> 0`。

已改：`svg_real` 例外保留 0 值，且只在页面真有 `<svg>` 标签时才报这一项。

> 教训：**过滤器和检测器要一起报。** 只报过滤后的数字，等于把「我滤掉了多少」
> 藏起来。这也解释了为什么 2026-10-03 那次回归里 schoolphoto2026 的 `svg_real`
> 从「不显示」变成了「显示 0」—— 那是**信息变多了**，不是数据变了。

### 13. `decl()` 取不全**含 HTML 实体**的值 ⭐（2026-10-11 已修）

```python
m = re.search(r'(?:^|;)\s*%s\s*:\s*([^;]+)' % prop, style)
```

`([^;]+)` 遇到第一个分号就停。而 HTML 实体 **`&quot;` 自带一个分号** —— 于是：

```
decl(s, 'background')           # s = 'background:url(&quot;http://a/b.png&quot;) center center'
  -> 'url(&quot'                 # 就这 9 个字符，后面的全丢了
```

**凡是值里含 `&quot;` 的声明都取不全**，至少两类：
- `background` / `background-image` 的 `url("…")`
- `font-family: Optima, &quot;Microsoft YaHei&quot;, sans-serif`

影响面：凡是用 `decl()` 判「值里有没有 / 值是什么」的地方都会被误导。
已知 `bgimg_rule` 用的是 `background-size`（值 `100% 6px`，不含实体）所以没受影响；
**下次谁再用 `decl()` 去解析 URL 或字体名就会踩。**

**处置**（2026-10-10 挂账，2026-10-11 修）：取值时**先整体吃掉实体再找真正的分号**。

```python
_ENTITY = r'&(?:[a-zA-Z][a-zA-Z0-9]*|#[0-9]+|#[xX][0-9a-fA-F]+);'
# decl(): ([^;]+)  →  ((?:%s|[^;])+)  % _ENTITY
```

命名实体（`&quot;`）和数字实体（`&#39;` / `&#x27;`）两种写法都覆盖。

**同一个 bug 在 `parse_tokens` 里还有一份独立的**：`font-family:\s*([^;"\']{4,90})`
也是撞到实体的分号就停 —— 它**不走 `decl()`**，所以只修 `decl` 修不好它。
两处都改了，顺带把 90 字符的上界提到 200（完整字体栈本来就长过 90）。

修复效果（4/9 个模板的 `font_families` 之前是残渣）：

| 模板 | 修复前 | 修复后 |
|---|---|---|
| `damanguan2026` | `mp-quote, &quot` ×132 | `mp-quote, &quot;PingFang SC&quot;, system-ui, …` |
| `redcard2026` | `-apple-system, BlinkMacSystemFont, &quot` ×31 | `-apple-system, BlinkMacSystemFont, &quot;PingFang SC&quot;, …` |
| `newsblue2026` | `&quot` ×1 | `&quot;PingFang SC&quot;, system-ui, …` |
| `papertoday2026` | `Optima, &quot` ×1 | `Optima, &quot;Microsoft YaHei&quot;, PingFangSC-regular, serif` |

> **注意：值里的 `&quot;` 不做解码**，保留原样。这是有意的 —— 库里写着「照抄样式的
> 字符串，别自己重写」，而 `&quot;` 正是把它贴回 style 属性时**必须**的写法。
> 解码成裸引号反而会让这个值不能直接用。

**实测影响面**（对 9 个样本逐个对拍）：改了 `font_families`（4 个模板），
**另外还改了两处 `bgimg_any` 的 note** —— 这一条值得单独记：

| 模板 | note 里的 base64 data URI 计数 |
|---|---|
| `graylist2026` | 0 → **2** |
| `schoolphoto2026` | 0 → **4** |

`_bg_du` 那句是 `'data:' in decl(s, 'background')`，取值被截断成 `url(&quot` 之后
**永远匹配不到 `data:`，那一项恒为 0** —— 而本文档「已知边界」里那张手工测量表早就写着
`graylist` x2、`schoolphoto` x4。**工具现在才追上当初的手工测量**，
两者由完全不同的方法得出（一个是正则统计，一个是人眼数 + `sample.html` 里翻），
对上了就是互相佐证。

> ⚠️ **自曝一个工具盲区**：我自己的对拍脚本只比 `count`，**没比 `note` 和 `variants`**，
> 所以这两处变化在提交前**没被对拍发现**，是提交后逐文件核 diff 才看见的。
> 对拍要比**整个 entry**，别只比那个数字 —— 「数字没变」不等于「这一项没变」。
> （同缺陷 12 的教训：过滤器和检测器要一起报，`note` 里往往就藏着被滤掉的那部分。）

> 教训 ——「我以为我在修一个新 bug，其实踩在一个更老的 bug 上」：
> 第一版 `_has_bgurl` 写的是 `'url(' in decl(...)`，**恰好还能工作**
> （截断成 `'url(&quot'` 之后仍然含 `url(`）。我把它「收紧」成要求完整匹配 `url(...)`，
> 结果全军覆没、`bgimg_any` 整项消失。是**前后对比**把它暴露出来的 ——
> 只看单个模板的结果，只会看到「这一项没了」，看不出为什么。
>
> 补一条：**同一个形态的 bug 会有多个副本**。这次修的时候顺手搜了一遍
> `[^;]` / `[^;"]` 的写法，才发现 `parse_tokens` 里那份独立存在。
> 修一个「既有缺陷」时，先问「同样的写法还在别处出现过吗」。

### 14. `accent_text` 从不检验「是不是彩色」 → 全库虚高 ⭐（2026-10-10 已修）

原判据是：

```python
n_acc = len(re.findall(r'<(?:strong|span)[^>]*color:\s*(?:rgb|#)[^;"]{3,30}', html, re.I))
```

它的 label 写着「强调色文字（strong/span 带**彩色**）」，但判据**只看有没有
`color: rgb…` 这个语法，从头到尾没有检验过颜色本身**。而且分支里的 `rgb`
还会匹配上 `rgba(` 的开头（`rgba` 以 `rgb` 起头，正则不设边界）。

实测 `damanguan2026`：命中的 133 处里 **132 处是 `rgba(0, 0, 0, 0.9)` 纯黑**，
报出来的却是「强调色文字 133 处」。全库都被抬高：

| 模板 | 旧 | 新 |
|---|---|---|
| `aifrontline2026` | 175 | **11** |
| `damanguan2026` | 133 | **0** |
| `redcard2026` | 66 | **27** |
| `graylist2026` | 46 | **1** |
| `papertoday2026` | 27 | **22** |
| `newsblue2026` | 25 | **3** |
| `orisynth2026` | 18 | **12** |

修法要**同时**满足四条，少一条就会在新数值里留下另一类错：

1. 真去解析颜色，按通道差判彩色（`is_chromatic`，阈值 24）。
2. 按每个元素**最后一条** `color` 声明算 —— 同一段 style 里后写的生效。
   只取第一个会漏（`aifrontline` 有 4 个标签写着 `白 …; 青绿`，
   渲染是青绿）也会误报（`papertoday` 有 21 个标签写着 `紫 …; rgba(0,0,0,0.4)`）。
3. `color:` 前必须**不是 `-` 也不是字字符**（`(?<![-\w])`）。不加的话会匹配到
   **别的属性的后缀**：`border-color:`（papertoday，而同一段 style 里 `border-style:none`，
   边框根本不画）和几乎所有 span 都带的 `-webkit-tap-highlight-color:` 都会被算进来。
4. 只在**真正的 `style` 属性**里找。`data-pm-slice` 这类属性里塞着编辑器元数据 JSON
   （内含 `&quot;style&quot;:&quot;…color: rgb(66,133,244);&quot;`），扫整个标签会
   把**编辑器存的样式副本**当成生效样式（aifrontline 就多算 1 个）。
   注意 `data-original-style=` 里也含 `style="`，同样要用 `(?<![-\w])` 挡住。

> 教训 ——「判据要匹配**语义上的那个东西**，而不是它的**字面形态**」。这一条在库里
> 已经被犯过很多次（#6 数标签、#7 数前缀、#11 数 viewBox），这次连续犯了四层：
> 语法 ≠ 颜色、第一个声明 ≠ 生效声明、属性后缀 ≠ 属性、属性里的文本 ≠ 生效样式。
>
> 另一条：**大降幅必须独立复核**。改完第一版时 aifrontline 报 6、papertoday 报 22，
> 我另写一套（把 style 按 `;` 切开、按属性名精确取 `color`）才对出来 11 / 22 ——
> **第一版是错的**（漏 5 个 blue 的 `!important` 写法）。只看被测实现自己的数字，
> 一路上四个错版本看起来都「挺合理」。

### 15. `<mpcpc>` 被当成「文章链接卡片」 → 名字、含义、数量三样都错（2026-10-10 已修）

```html
<mpcpc class="js_cpc_area res_iframe cpc_iframe" ... src="/cgi-bin/readtemplate?t=tmpl/cpc_tmpl#..." style="display: none;">
```

`<mpcpc>` 是**微信的 CPC 广告位**，属于平台家具（且 `display:none`），
却被登记成 `('mp_article', '文章链接卡片')`。
而这篇**真正的**文章链接是 `<a class="normal_text_link mp_article_text_link">` ×3，
**检测器一个都没认出来**。于是 `mp_article: 2`：名字不是文章链接、实物是广告位、
数量也不是真链接数。已改为 `mp_cpc_ad` + 新增 `article_link`。

**顺手拆掉的一个更隐的坑**：`mp_known` 原本写成
`sum(v['count'] for k,v in comps.items() if k.startswith('mp_'))`
—— **靠键名前缀猜「这是不是 `<mp*>` 组件」**。新加的 `article_link` 若命名成
`mp_article_link`，就会被算成已知 `<mp*>`，把 `mp_other` 的计数吃掉甚至算成负数，
真实的 `<mp-style-type>` 就不报了。已改成**按标签精确累加**，与键名叫什么无关。

> 教训：**前缀/命名不能承担语义**。判据要绑在被数的那批东西本身。

### 16. 编辑器留下的**样式副本**被当成生效样式统计 ⭐（2026-10-11 已修）

微信编辑器会在标签上留两个属性：

| 属性 | 是什么 |
|---|---|
| `data-pm-slice` | 一段 JSON，里面 `&quot;style&quot;:&quot;…&quot;` 记着**当时的**样式 |
| `data-original-style` | 该元素**保存时**的样式 |

它们**都不是生效样式** —— 生效的是 `style` 属性本身。但 `parse_tokens` /
`analyze_structure` / `detect_components` 都是拿正则**扫整个 HTML**，
于是副本里的颜色、边框、尺寸、对齐全被算成了模板的一部分：

| 模板 | 症状 |
|---|---|
| `aifrontline2026` | 多出一个**假主色** `#3f3f3f`（×2，只存在于元数据） |
| `papertoday2026` | `rgba(0, 0, 0, 0.4)` 记 135，真实 83；`box-shadow` 26 → 13；`displays block` 38 → 24 |
| `damanguan2026` | `rgba(0, 0, 0, 0.9)` 135 → 132；结构 `text-align:justify` 3 → **0** |
| `graylist2026` | `line_heights` 的 `1.5em`×15 整项消失（只在元数据里） |

还有一层副作用：`data-original-style="width: 60px"` 里**也含 `style="`**，
所以找 `style="` 的正则（`detect_components` 的 `allstyles` 池）会**匹配到副本**
而不是真样式。

**修法**：加 `strip_meta(html)` 去掉这两个属性，并让它**在每个统计函数的入口调用**
（幂等），而不是只在 `main()` 里做一次 —— 否则将来谁直接调 `parse_tokens(html)`
就会静默拿到污染结果。`sample.html` 里存的仍是**原始 html**，只有统计走干净版。

> 实测效果里有一条值得记：修完之后 `aifrontline2026` 的 `margin` 里**冒出了新值**
> （`8px 0px 24px`、`8px 0px 0px`）。那不是「多算了」，而是原本被虚高项挤掉的真值
> **终于进了 top-N** —— 污染不只会造假，还会**把真数据挤到看不见**。

> 教训：**「HTML 里出现的样式」≠「生效的样式」**。同一个元素上可能有好几份样式文本，
> 只有一份是真的。同缺陷 14 的第 4 条是一条根上的。

### 17. `letter_spacing` 只认 `px`，认不出 `em`（2026-10-11 已修）

```python
'letter_spacing': _top(re.findall(r'letter-spacing:\s*([\d.]+px)', html), 6),
```

旁边的 `line_heights` 写的是 `([\d.]+(?:px|em)?)` —— 同一个函数里，一个认 em 一个不认。
于是 `damanguan2026` 的真实字距 `0.034em`（×132）**从来没被记下来过**：
它的 `letter_spacing` 里原本那项 `0.578px` 反而是元数据里的假值（见缺陷 16），
两个 bug 叠在一起，正好掩盖了彼此。

已改成 `([\d.]+(?:px|em|rem)?)`，补回三处真值：
`damanguan2026` `0.034em`×132、`newsblue2026` `0.034em`×1、
`papertoday2026` `0em`×25 + `0.02em`×21。

> 教训：**同一个函数里并排的两个判据要互相看齐**。`parse_tokens` 里 9 个令牌
> 各写了各的正则，其中一个的写法比邻居窄 —— 这种不一致不会报错，只会静默少记。

## 已知边界

- **只反推样式，不搬运内容**。`sample.html` 是留作对照的，别整段复用 ——
  那是别人的文章。抄版式可以，抄文字不行。
- **图片不处理**。`sample.html` 里的图是原站的 CDN 链接（`mmbiz.qpic.cn`），
  换文章时必须替换。
- **`preview.png` 需要外部提供**（`--preview`）。脚本自己截图要起浏览器，
  目前没内建；用 browser-act 截一张传进来即可。
- 微信会剥 `<style>` 和 `class`，所以**所有样式必须内联** —— 这是
  `clz_docx_to_mp` 那条流水线的硬约束，本库的产物要喂给它，同样受约束。

- **`--out` 指向不存在的目录会崩**（2026-10-10 发现，未修）。`main()` 里 `find_duplicate()`
  在 `os.makedirs(outdir)` **之前**就 `os.listdir(out_dir)`，于是报
  `FileNotFoundError: 系统找不到指定的路径`。先手工建好目录即可绕过。

- **背景图构件只分类了一半**（2026-10-03 记录，并实测过一轮）。
  `bgimg_any` 只数得出「有几个元素挂了背景图」，`bgimg_rule` 只认得「被拉成细长条
  当线」的那一种。剩下的分不出「拿图当构件」和「普通配图」。

  量过一轮候选判据「**同一张图被反复使用**」（7 个模板，看 `sample.html`）：

  | 模板 | 带背景图的 style | 去重后 | 重复使用的图 |
  |---|---|---|---|
  | `aifrontline2026` | 10 | 6 | **x4 章节横线**（真构件）+ x2 视频卡片头像（平台家具） |
  | `autumn2026` | 19 | 12 | x4 + 四组 x2，都是 `background-size:100% 100%` 的容器 |
  | `graylist2026` | 3 | 2 | x2 一张 base64 data URI |
  | `schoolphoto2026` | 5 | 2 | x4 **同一张 base64 data URI** |
  | `newsblue` / `papertoday` / `redcard` | 0 | 0 | — |

  **结论：复用是真信号，但单独用不够。** schoolphoto 的 x4 与 graylist 的 x2 是
  **同一张 base64 空白占位图**（1x1 间隔图），根本不是构件 —— 只看复用次数会把它
  误判成构件。真正稳的判据是**几何形状**（`bgimg_rule` 那样看 `background-size`），
  这与本文档反复出现的那条一致：**判据要选语义上必然不同的维度，别用会重叠的连续量。**

  > 顺带：`bgimg_any` 的 note 现在会把 base64 data URI 单列出来 ——
  > 实测那类多是空白占位图，混进总数会让人以为「这个模板用了 N 张背景图」。

  **下次收模板优先撞这个**：还需要一两个「用背景图做构件」的样本，才能定
  `background-size: 100% 100%` 的容器（autumn 那五组）到底算构件还是算配图。
